# Django MVP: фазы 0–1

Объём согласован 10 ноября 2026: MVP, без подключения внешних провайдеров. Основной бизнес-контур теперь работает на Django REST Framework. Next.js сохраняет существующий интерфейс, а серверные чтения и изменения в режиме `DATA_SOURCE=django` обращаются к DRF. Supabase и mock оставлены отдельными режимами совместимости.

## Локальный запуск

Backend — самостоятельный Python-репозиторий. Нужны Python 3.12 или `uv`; Node.js для API не нужен.

```bash
git clone https://github.com/ibrodevs/AI-Manager-backend.git
cd AI-Manager-backend
./scripts/dev.sh --demo
```

API: `http://127.0.0.1:8000`, Swagger: `http://127.0.0.1:8000/api/docs/`. Скрипт печатает случайный пароль локального демо-аккаунта. При первом входе собственник настраивает TOTP через frontend; до подтверждения кодом сессия не выдаётся.

Frontend запускается из отдельного репозитория `https://github.com/ibrodevs/AI-Manager`:

```bash
cp apps/web/.env.django.example apps/web/.env.local
npx pnpm@10.33.0 install --frozen-lockfile
npx pnpm@10.33.0 dev
```

Значения во frontend: `DATA_SOURCE=django`, `DJANGO_API_URL=http://127.0.0.1:8000/api/v1`. Браузер обращается к Next.js, а Next.js — к Django, поэтому токены остаются на сервере frontend и CORS для этой схемы не нужен.

SQLite предназначена только для разработки; для RLS используйте PostgreSQL. Для пустой компании вместо демо:

```bash
DJANGO_DEBUG=1 .venv/bin/python manage.py provision_company --email owner@example.com --name 'Моя компания'
```

Для сотрудника добавьте `--company-id COMPANY_UUID --role staff` или создайте приглашение в кабинете. `seed_demo` запрещён вне DEBUG.

## Возможности бизнес-контура

- Компании, филиалы, членство в нескольких компаниях, четыре роли, серверная матрица прав. Чужие объекты возвращают 404; внешние ключи и списки идентификаторов проверяются на принадлежность компании. Сотрудник читает только назначенные ему заявки, звонки и чаты; бухгалтер не читает CRM.
- Сессии с хешем токена в БД, сроком 12 часов и немедленным отзывом. Next.js хранит токен в httpOnly cookie. Обязательная TOTP для собственника и суперадминистратора, шифрование секретов, защита от повторного кода. Список сессий и выход со всех устройств.
- CRM: контакты по E.164, заявки, номера внутри компании, статусы, причины отказа, комментарии, история, объединение контактов, экспорт JSON, удаление данных контакта.
- Анкета: все 15 блоков, взвешенный индекс, услуги, сотрудники, FAQ, черновик, неизменяемые опубликованные снимки, последовательные версии и откат новой публикацией. AI-тест читает опубликованный снимок. Адреса и график из анкеты синхронизируются с основным филиалом.
- Ассистент без ключей использует явно обозначенный ограниченный локальный движок. Цены берутся из структурированных полей. Тестовый диалог хранится в Django; созданная им заявка настоящая. Диалог нельзя подтвердить после перехвата или конкурентного изменения.
- Inbox: сообщения и история в БД, перехват, возврат AI, черновики, закрытие и заявка из чата. В режиме без модели входящие передаются человеку. Внешняя отправка запрещена без подключённого канала. Окно Meta проверяется на сервере; произвольное имя шаблона не обходит запрет.
- Календарь: ресурсы, запись, перенос, отмена; блокировка ресурса в транзакции и PostgreSQL exclusion constraint. Часовой пояс компании вместо фиксированного UTC+6. Для поликлиник: талоны, FIFO-очередь, предложение на 15 минут, принятие, отказ и автоматическое истечение.
- Звонки: хранение карточек и расшифровок, оценки, отметка перезвона; входной подписанный контракт события `call.ended`, идемпотентность и округление вверх до 15 секунд.
- Биллинг MVP: подписки и счета назначает платформа. Минуты и диалоги считаются по реальным данным. Покупка пакета без оплаты не увеличивает баланс. Реальная линия не включается без активной компании, оплаты и опубликованной анкеты от 70%.
- Уведомления внутри приложения, durable outbox, Celery worker/beat, SSE кабинета из событий БД. Для ненастроенного провайдера статус `unconfigured`, без ложного `sent`.
- Отчёты по настоящим звонкам и заявкам, очередь обращений, требующих внимания. Пустая база не заполняется случайными метриками.
- Платформенная консоль Django Admin, доступная только суперпользователю с TOTP; аудит действий. Старая mock-суперадминка Next.js закрыта в Django-режиме.

## API

Swagger: `http://127.0.0.1:8000/api/docs/`, OpenAPI: `/api/schema/`, сохранённая схема: `openapi.yaml`.

- `POST /api/v1/auth/login/`: email, password, необязательный otp. Первый ответ собственнику содержит запрос 2FA, затем выдаётся токен.
- `GET/DELETE /api/v1/auth/session/`, `GET/DELETE /api/v1/auth/sessions/`.
- Ресурсы `/api/v1/contacts/`, `/leads/`, `/branches/`, `/services/`, `/staff/`, `/faq/`, `/resources/`, `/tickets/`, `/invoices/`, `/calls/` с пагинацией. Возможность записи зависит от роли и ресурса; звонки создаются только подписанными событиями.
- `GET /api/v1/read/NAME/`: адаптер существующего кабинета. `POST /api/v1/commands/NAME/` принимает `{ "args": [...] }`.
- `GET /api/v1/events/?after=CURSOR`, `GET /api/v1/export/`.
- `POST /api/v1/provider-events/`: нормализованный входной контракт шлюза. Выключен (503), пока не задан `WEBHOOK_SECRET`.

С заголовком `X-Company-ID` выбирается одна из компаний пользователя. При отсутствии берётся первое активное членство. Идентификатор сам по себе не даёт доступ.

Подпись входного события: `X-Webhook-Timestamp` — Unix timestamp, `X-Webhook-Signature` — hex HMAC-SHA256 от `timestamp + '.' + raw_body`, ключ `WEBHOOK_SECRET`. Допуск времени 5 минут. Тело включает `companyId`, уникальный `eventId`, `kind`. Для `chat.inbound`: `channel` (`widget`/`telegram`), `externalId`, `body`, опциональный `verifiedPhone`. Для `call.ended`: `externalId`, `caller`, `durationS`, опциональные `kbVersion`, `summary`, `outcome`. Повтор события не создаёт повторных сущностей. Это контракт для будущего шлюза, а не готовый коннектор оператора связи.

## PostgreSQL и Docker

`compose.yaml` содержит PostgreSQL 16, Redis, мигратор, DRF, Celery worker и beat. Frontend запускается и развёртывается отдельно. Задайте в неотслеживаемом `.env.docker` (шаблон `.env.docker.example`) четыре независимых значения: `POSTGRES_PASSWORD`, `DATABASE_RUNTIME_PASSWORD`, `DATABASE_WORKER_PASSWORD`, `DJANGO_SECRET_KEY` (например, hex-строки из генератора секретов).

```bash
docker compose --env-file .env.docker up --build -d
```

Мигратор использует отдельную привилегированную роль. API использует `allmanager_runtime`; worker/beat — `allmanager_worker`. Обе роли без SUPERUSER/BYPASSRLS. Только worker имеет разрешение перечислить компании для планирования заданий; остальные данные он обрабатывает в контексте конкретного тенанта. На таблицах клиентов включены ENABLE и FORCE RLS. Контекст компании устанавливается только после проверки членства и действует внутри транзакции. Административный контекст устанавливается только для MFA-сессии суперпользователя. Не запускайте API с ролью мигратора.

Для provisioning и создания администратора запускайте management-команды с URL роли мигратора. Секрет шифрования 2FA (`DJANGO_SECRET_KEY`) храните стабильно и включайте в защищённую процедуру резервирования; его замена без миграции секретов сделает устройства 2FA недоступными. Начальная настройка суперадминистратора:

```bash
python manage.py createsuperuser
python manage.py enrol_mfa --username ADMIN_USERNAME
```

Статические файлы Django Admin собираются в образе и обслуживаются WhiteNoise. Порты Compose привязаны к localhost. Для внешнего запуска нужен TLS reverse proxy и корректные домены/secure cookies. Docker Compose в текущей сессии не запускался: Docker на машине отсутствует. Приложения проверены нативно.

## Проверки

```bash
DJANGO_DEBUG=1 .venv/bin/python manage.py test core --noinput
# Для всех тестов, включая RLS и ограничения БД:
DATABASE_URL=postgresql:///TEST_DATABASE DJANGO_DEBUG=1 .venv/bin/python manage.py test core --noinput
DJANGO_DEBUG=1 .venv/bin/python manage.py makemigrations --check --dry-run
DJANGO_DEBUG=1 .venv/bin/python manage.py spectacular --file /tmp/schema.yaml --validate --fail-on-warn
```

Браузерный набор использует локальную компанию из `seed_demo`, проверяет 2FA, создание заявки с независимым чтением REST, экраны кабинета, заявку от ассистента, сохранение настроек и отказ при неверном пароле. Для повторного прогона передайте секрет тестового устройства через `E2E_TOTP_SECRET` либо используйте чистую тестовую БД. Рабочие секреты использовать в тестах нельзя.

CI backend запускает PostgreSQL, тесты API/RLS, проверку миграций и OpenAPI. TypeScript и сквозные браузерные тесты находятся в репозитории frontend; там CI дополнительно получает checkout backend. Локальное выполнение CI-файла не означает, что удалённый GitHub Actions уже завершился.
